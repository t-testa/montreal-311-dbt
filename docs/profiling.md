## Data quality issues

1. **Missing key for 45.5% of rows.** `ID_UNIQUE` is null on all 1,467,174 'Information' contacts (and they also have no `DERNIER_STATUT`, location or borough). Only 1,756,293 rows can be identified.
2. **Exact duplicate rows.** 713 distinct row patterns repeat, 713 surplus rows in total (Information: 713). Rows with an ID are unique, so the duplicates are keyless rows that cannot be told apart from genuine repeat calls.
3. **ID format is not uniform.** 1,838 IDs carry an `-A`/`-B` suffix (1,756,293 distinct IDs collapse to 1,756,282 once the suffix is stripped), and ID lengths range from 4 to 11 characters. 3 IDs start with `20-`/`21-` even though all rows are created in 2022 or later.
4. **Two borough columns that disagree and use different formats.** `ARRONDISSEMENT` writes `Mercier - Hochelaga-Maisonneuve` (887,333 rows use ` - `) while `ARRONDISSEMENT_GEO` writes `Mercier-Hochelaga-Maisonneuve`. 7. **`PROVENANCE_*` columns are counts, not flags.** Values go up to 60 per row, despite looking like 0/1 channel flags; `PROVENANCE_ORIGINALE` is null on 1,839 rows.
8. **Timestamps are ISO strings without a timezone** (`2023-07-10T20:15:39`, always 19 chars). All-text storage means dates, coordinates and counts all need explicit casting in staging.
